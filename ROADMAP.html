FeatherBrowser · engine plan · rev 2

Rebuilding Feather

The tab-suspension engine works and is well tested. The three privacy subsystems do not run at all — not because they were written badly, but because wry 0.47 exposes no hook for subresource requests, which is the layer all three were designed to sit on. This plan fixes that with the cheapest mechanism that actually works, then builds outward until Feather is something you can browse with for a day.

The one decision that sets everything else

How the network layer gets intercepted

adblock::Engine is currently consulted only from with_navigation_handler, so it sees top-level navigations and nothing else. Every ad, beacon and tracker a page loads passes straight through. wry 0.47.2 offers exactly three network-adjacent hooks — with_custom_protocol, with_asynchronous_custom_protocol, and with_proxy_config. None of them intercepts an ordinary https:// subresource. There are two ways out.

Lane A — WebKit content rules

Take this

Compile the filter lists into WebKit's own content-blocking JSON and hand them to WKContentRuleListStore through an objc2 bridge on the webview handle. Blocking then happens inside WebKit's network stack — the same mechanism Safari content blockers use.

  • The adblock crate you already depend on ships the converter: feature content-blocking in 0.8.12 emits exactly this syntax.
  • Zero per-request Rust cost, no certificate, no MITM, nothing in the trust store.
  • Ceiling: block, block-cookies, hide-element, force-HTTPS. It cannot rewrite a query string.

Lane B — loopback MITM proxy

Defer

Run hyper + rustls on 127.0.0.1 behind a generated local CA and point the webview at it with with_proxy_config. Total control of every byte: block, strip params, substitute bodies, upgrade scheme.

  • Costs a CA installed in the system trust store — a genuine security surface, and a UX cliff on first run.
  • You inherit TLS termination, cert-error handling, and per-platform trust plumbing forever.
  • Buys one thing Lane A lacks: query-param stripping on subresources, where trackers are rarest.

Lane A delivers most of the privacy value for roughly a fifth of the work and none of the risk. Tracking parameters still get stripped where they actually appear — top-level navigations — by the repaired UrlCleaner in Phase 0. Lane B stays on the shelf as Phase 6, gated behind evidence.

Repair

Three live defects and 128 lines of code that can only do harm.

  • Re-encode cleaned URLs. clean_url decodes query pairs and reassembles them raw, so redirect_uri=https%3A%2F%2F… comes back out as a literal ? and &. Every OAuth login it touches breaks. Swap the hand-rolled builder for query_pairs_mut().clear().extend_pairs(…), which encodes on write.

  • Fix the tab-id stamp. create_tab guesses total_tab_count() + 1 while the store hands out a monotonic id — they diverge the moment a tab closes, and scroll and title updates land on the wrong tab. Expose peek_next_id().

  • Version the repo. git init, a .gitignore for target/, sessions.db and .DS_Store, and a README whose claims match the binary.

The ad blocker actually blocks

Lane A, wired end to end.

  • Build step. Fetch EasyList and EasyPrivacy, parse with adblock, convert with the content-blocking feature, cache the compiled rule list on disk keyed by the source-list hash so startup never pays for it twice.
  • Platform bridge. src/platform/macos.rs — objc2 call into WKContentRuleListStore.compileContentRuleList, attach the result to each webview's WKUserContentController at build time.
  • Keep the Rust engine for navigations. It is already correct there; it just was never the whole story.
  • Surface it in the topbar. The feature is invisible otherwise, and invisible features get quietly regressed. A per-request tally turned out to be unbuildable — WebKit's rule engine blocks inside its networking layer and reports nothing back to the host — so the shield shows the live rule count and lights up when the lists are attached. A "requests blocked" number here would have been invented.
At the end of phase 01

Ads and trackers are blocked on every subresource a page loads, inside WebKit's networking layer, against 107,987 real EasyList and EasyPrivacy rules instead of 19 hand-typed domains. The topbar shield lights up with the rule count once WebKit has them. This is the phase where the project's headline claim becomes true.

One thing the plan got wrong: a single rule list could not hold the lists. The first cut capped at 50,000 rules and dropped the overflow — which, because EasyPrivacy sorts last, quietly discarded almost the entire tracker list. The rules are now split into chunks of 25,000 and handed to WebKit as five lists, which WKUserContentController accepts without complaint. Nothing is dropped.

Sessions that survive

The SQLite layer writes faithfully and is never read. Make it real.

  • Stable ids. next_id restarts at 1 every launch, so a new session's tab 1 upserts over the last session's tab 1. Persist the counter, or switch to UUIDs.
  • Restore on boot. load_snapshots_from_db is called from nothing but tests. Rebuild the tab tree at startup and rehydrate each dormant tab lazily on first focus.
  • Delete rows on close, so the table reflects what is open rather than everything that was ever dormant. Not on rehydrate, though — see below.
  • Move the database out of the working directory into the platform data dir — today the session you get depends on where you launched the binary from.
  • Capture form state. The form_data column, the struct field and the spec requirement all exist; nothing ever writes them.
At the end of phase 02

Kill the process and reopen it: every tab is back, hibernated, at the scroll position it had, with half-finished form fields intact and the tree hierarchy preserved. Hibernation stops being a memory trick and becomes the thing that makes 40 open tabs survivable — a restored session renders exactly one WebView, the tab that was in front, no matter how many tabs it holds.

Two departures from the plan. The snapshot table is now the session, not the dormant set: every open tab is written, because a tab that was still live when the process died has to come back too — which is also why rows are not deleted on rehydrate, only on close. And form contents cannot be collected at suspension time, since hibernating means dropping the WebView synchronously and there is no moment left to ask the page anything. The page volunteers its fields with the state report it already sends on scroll, and the host persists the last thing it heard. Passwords, hidden fields and autocomplete="off" are never collected, and a navigation drops what was typed so it cannot be replayed into an unrelated page with the same field names.

A ceiling you can prove

Replace the 120 MB claim with a measurement.

  • Instrument RSS via mach_task_basic_info, exposed behind a --profile flag — plus the WebKit processes, which is where the memory actually is. WKWebView renders out of process and the XPC services are reparented to launchd, so they are neither visible to task_info nor our children. Measuring only the engine would have produced a flattering number that meant nothing.
  • Derive the ceiling from available RAM with a configurable cap, instead of a hardcoded MAX_ACTIVE_VIEWS = 2. Two live views is punitive on a 64 GB machine and may still be one too many on 8 GB.
  • Bench harness. Open N tabs from a fixed URL set, sample RSS at each step, emit a table — the self-profiling summary the original spec asked for and never got.
At the end of phase 03

A real number in the README with the method next to it, and a ceiling that adapts to the machine it runs on. Memory discipline is the entire reason this project exists rather than being another Electron shell — so it should be the best-instrumented part of the codebase, not the only unmeasured one.

The curve is the thesis, and it holds: on an 18 GB machine the ceiling comes out at four live views, and total memory climbs to 822 MB at six tabs and then falls to 577 MB at ten, because the extra tabs are hibernated rather than rendered. Ten tabs cost less than six.

It also cost the original spec's headline claim. Under 120 MB with five tabs was never true: five tabs cost about 760 MB all in. What is true — and now measured rather than asserted — is that the number stops growing.

And the instrumentation immediately paid for itself. The engine process was sitting at 327 MB before a single page loaded. Converting EasyList to WebKit's format allocates several hundred megabytes that the allocator never hands back, and it was happening on every launch. WebKit already keeps compiled lists in its own store, so a manifest of identifiers now lets a warm launch ask for them directly without touching a filter list: baseline 326.9 MB → 96.4 MB. It also closed the startup window from phase 01 — rules now attach before the first page finishes loading.

Verified →--bench=10 on an 18 GB machine, release build, real pages: 188.8 MB at rest, 681.9 MB at four tabs, 577.1 MB at ten. 31 tests · clippy clean

A runtime that behaves

Today runtime.js takes ownership of every page it lands on.

  • Vim keys become opt-in. Bare t, x, f and o are preventDefaulted globally, so typing on GitHub opens tabs. Gate behind a toggle, default off, with a per-origin denylist. Extend isEditable to role="combobox", role="searchbox" and shadow roots.
  • Throttle the consent observer. It runs 16 querySelectorAll sweeps of the whole document on every DOM mutation — thousands of full scans a second on a React app. One requestAnimationFrame pass with a dirty flag. Drop [aria-label*="cookie" i], which deletes real content on any page that discusses cookies.
  • Teach it about SPAs. Patch pushState/replaceState and listen for popstate. Right now a single-page app's title never reaches the tab strip and its snapshot rehydrates to the wrong URL.
  • Persist dark mode per origin in SQLite and reapply on load, instead of losing it at every navigation.
At the end of phase 04

Feather stops fighting the pages it renders. Site keyboard shortcuts work, heavy apps stop stuttering, tab titles track SPA navigation, and dark mode remembers the sites you asked it for.

The gate came out as per-site opt-in rather than a global switch with a denylist — strictly safer, since a site is silent until you press the ⌨ button on it, and the two mechanisms would have needed the same storage anyway. That storage is a site_prefs table keyed by origin, which dark mode uses too. The page asks the host for its preferences rather than the host pushing them, because a tab's origin changes under the host on every link click and every SPA route, and the page is the side that knows when.

The throttle turned out to be hiding a second bug: the sweep forced overflow: auto and position: static on <body> every time it ran, whether or not it had removed anything — overriding the layout of every page that never had a banner. It now only does that after actually removing one.

The things that make it a browser

Mostly UI over what WKWebView already does. Cheap, and the difference between a demo and a tool.

  • Per-tab back and forward — history exists in the webview; it has no keybinding and no button.
  • Find in page, zoom, and a context menu with open-in-new-tab and copy-link.
  • Downloads with a destination prompt and a visible progress row.
  • Favicons in the tab strip — at 90 px per tab, a globe emoji on every tab is unreadable past four.
  • Bookmarks reusing the history table and the omnibar ranking already written in search.rs.
  • Link-hover status, so you can see where a link goes before you commit to it.
At the end of phase 05

A browser you can use for a full day without reaching for Safari — and the point at which the hibernation engine stops being a demo and starts paying you back, because you finally have enough tabs open for it to matter.

Back and forward are history.back() in the page rather than a platform call, which costs nothing and works on every target. Zoom is wry's zoom(), held per tab in memory and not persisted. Downloads use wry's two handlers with a real NSSavePanel run modally from inside WebKit's own download callback — which is also where the one real bug of this phase was: WKDownload refuses a destination that already exists, so confirming "replace" in the panel produced a download that failed with cancelled and no explanation. The panel's answer is now honoured by removing the file before returning.

Find-in-page was the interesting one. window.find searches the rendered document, which includes the query field you are typing into — a bar built the obvious way reports a match for any string, because the string is on screen. The bar now lives in a shadow root, which window.find does not walk. It also takes no focus at all: a focused field owns the document selection, and window.find resumes from the selection, so stepping between matches only works while the matches themselves hold it. The cost is a query field with no caret, no paste and no IME.

Two departures from the plan. Favicons come from each site's /favicon.ico rather than the <link rel=icon> the page declares — three of four real sites answer, and the fourth keeps the globe. Bookmarks are a flag on the history table rather than a table of their own, which is what "reusing the history table" turned out to mean literally: one column, one ORDER BY, and starring a page you have never visited creates the row.

Verified →a probe page in the running browser: find steps forward and backward between two matches 2,700 px apart and types while a page text field has focus, without touching it; a string present only inside the query field is reported as no match; right-click on a link suppresses WebKit's menu and offers two items, right-click on text does not; hovering a link shows its target and leaving hides it; pushState ×2 then back, forward and go(-2) all land correctly; two zoom steps narrow the layout viewport and reset restores it; a 400 KB download over a replaced destination logs start then ok with a matching md5; favicons for github.com, wikipedia.org and news.ycombinator.com load in the tab strip, rust-lang.org falls back. 36 tests · clippy clean

The proxy, if it earns it

Lane B. Do not start this without evidence.

  • Loopback hyper + rustls proxy behind a generated CA, wired via with_proxy_config.
  • Buys: query-param stripping on subresources, body substitution, scheme upgrade.
  • Entry gate: name three sites where Lane A demonstrably failed to block something that mattered. If you cannot, this phase does not happen.
The gate was run. It did not open.

Full control of every request — bought with a certificate authority living in the user's trust store, which is a permanent security liability for a marginal gain. My recommendation was that this phase stays unbuilt. The gate now says the same thing with evidence rather than an opinion.

Eight ad-heavy sites were loaded in the running browser with an audit script that collected every subresource the page actually requested, filtered it to known ad and tracker hosts, and re-tested each one. Zero tracker hosts appeared in the resource timing of any of them — cnn.com, forbes.com, dailymail.co.uk, weather.com, espn.com, speedtest.net and imdb.com each loaded 25–160 subresources, none of them from an ad or analytics host. ESPN's third parties were its own CDN and a consent banner; IMDb's were Amazon's image hosts and its own GraphQL.

The first run of this audit produced a failed control: a no-cors fetch of https://doubleclick.net/ resolved instead of rejecting, which would have meant the probe could not tell blocked from allowed and the zeros meant nothing. The control was wrong, not the browser. EasyList targets ad-serving paths and subdomains, not the bare apex. Re-run against real ad URLs, every one of ad.doubleclick.net/ddm/ad/x, pagead2.googlesyndication.com/pagead/js/adsbygoogle.js, google-analytics.com/analytics.js, googletagmanager.com/gtm.js, sb.scorecardresearch.com/beacon.js and ib.adnxs.com/ut/v3 was rejected, while example.com and a local server resolved. A real <script> tag pointed at adsbygoogle fired onerror.

Not one site could be named, let alone three. Phase 06 does not happen. The certificate authority does not get generated, and nothing goes into anyone's trust store.

Gate result →0 of 3 required failures found across 8 ad-heavy sites. The proxy stays on the shelf.

What gets cut, and why

The local CDN does not come back

It is tempting to fix the module rather than delete it — ship real jQuery and React bytes, rewrite CDN URLs through the custom protocol, keep the latency win. Don't.

Substituted bytes fail subresource integrity. A script tag carrying integrity="sha384-…" is checked against the bytes actually delivered, so the browser refuses to execute your local copy — and SRI is precisely what security-conscious sites put on their CDN scripts. You would be silently breaking the most careful sites on the web to save a few hundred milliseconds on the least careful ones, while owning a version-matching problem forever. Phase 1's blocking gets you the privacy outcome without any of that.

After phase 05

What you end up with

A browser

Back/forward, find-in-page, downloads, zoom, bookmarks, favicons, context menus. Enough that a working day inside it doesn't send you back to Safari.

That forgets on purpose

A hard ceiling on live WebViews, derived from the machine rather than hardcoded, with the rest of your tabs hibernated to SQLite at zero resident cost — and restored exactly, including scroll and form state, after a crash.

And blocks for real

EasyList and EasyPrivacy compiled into WebKit's own content-rule engine, running on every request, with tracking parameters stripped from navigations and a live count of what it caught.

Measured, not claimed

Live WebViews — adaptive, capped Dormant tabs — 0 MB resident RSS at 5 tabs — published with method Filter rules — full EasyList + EasyPrivacy Trust store — untouched Dependencies — unchanged from today

Nothing in Phases 0–5 adds a dependency to Cargo.toml beyond an objc2 binding, and Phase 0 removes more code than Phase 1 adds. The finished thing is smaller than the current one in every place except the parts that do the work.
